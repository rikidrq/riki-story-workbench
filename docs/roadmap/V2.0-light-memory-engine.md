# Riki 剧情工作台 V2.0 路线说明：轻量公共剧情记忆引擎

> 文档状态：方向设计稿，不代表已经实现、发布或完成真实酒馆验收。版本号用于表达产品阶段，不承诺具体发布日期。V2.0 只有在 V1.1 非数据库剧情工作台通过自动化、静态预览和真实 SillyTavern/Tavern Helper 验收后才进入实施。

## 一、版本定位

V2.0 的任务不是把现有重型记忆插件重新做一遍，而是在 V1.1 的剧情策划工作台和真实聊天之间补上一层足够可靠、足够透明、足够便宜的“公共剧情记忆”。所谓公共，是指它描述当前故事世界里已经发生、已经确认、仍需延续的共同事实；它不为每个角色分别推演主观认知，不维护庞大的关系图，也不试图替代角色卡、世界书、聊天正文或模型本身的上下文能力。它只解决一个具体问题：聊天变长之后，重要事实、未完线索、人物状态和章节承诺不应该因为上下文被截断而丢失。

这一版沿用 Riki 的基本原则：用户始终看得见系统准备记住什么、为什么召回它、它来自哪一楼、它何时被修改；自动化可以提出候选，但不能静默改写真相。记忆不再被包装成不可解释的“AI 大脑”，而被视为一组有来源、有状态、有生命周期、可撤销的剧情记录。它与 V1.1 的总纲、大章、小章、人物策划、推进预设和世界书条目相互引用，但不把这些成果复制成另一套权威。

V2.0 的产品口号可以概括为：少记、记准、找得到、删得掉。宁可漏掉一条低价值氛围描写，也不要把模型猜测写成事实；宁可在生成前少注入一条不确定记忆，也不要挤爆上下文；宁可让用户看到“本轮没有值得固化的内容”，也不要每轮制造一页摘要。

## 二、目标与成功标准

第一目标是让长剧情在低维护成本下保持连续。用户连续游玩多个章节后，模型仍能准确知道关键事件发生过没有、重要物品在哪里、谁答应了什么、当前未解决线索有哪些、已确认设定是否发生变化。这个能力必须建立在可追溯的本地记录上，而不是依赖无边界的历史全文回灌。

第二目标是保持轻量。默认路径不要求向量数据库、独立服务、Python 环境、显卡、云端 embedding 或持续运行的后台进程。基础召回应能在浏览器侧以确定性算法完成；模型调用只用于用户明确允许的候选提炼或阶段性压缩，并设有严格频率上限。即使关闭可选编译器，用户仍然可以手工标记、检索、编辑和注入记忆。

第三目标是可解释。每次请求前，用户都能展开“本轮记忆胶囊”，看到入选记录、排序原因、估算 token、来源楼层和冲突警告。每条记录都能跳转到来源，能被固定、降权、纠错、作废或从本轮排除。任何自动合并都产生 Diff 和可撤销版本。

第四目标是与 V1.1 解耦。V1.1 即使不启用记忆也必须完整运行；V2.0 以插件式服务接入 Command Core、上下文构建器和项目导出器。禁用或卸载记忆模块后，策划、模型配置、世界书读写、成果版本链和普通讨论仍然可用。

成功不能只用“页面能打开”证明。至少要有三类证据：确定性夹具证明提取、去重、冲突、召回与预算算法；长对话回放证明重要信息在截断后仍被正确召回且不会串聊天；真实手机和电脑端证明用户能检查、纠错、撤销、导出和关闭全部记忆入口。最终还要由驾驶员在一次真实长剧情中确认“少维护但连续性明显改善”。

## 三、明确非目标

V2.0 不做每角色独立记忆。角色甲知道而角色乙不知道、角色的误解、秘密传播、记忆衰退和主观情绪权重属于 V4.0。V2.0 的记录默认是项目层的共同叙事事实；若某条内容带有秘密，只能标记可见范围和注入限制，不能宣称已经拥有完整认知模拟。

V2.0 不做通用知识库或企业 RAG，不抓取互联网，不索引用户整个硬盘，不把所有世界书向量化。它也不建立复杂知识图谱、因果推理器、人格仿真器、长期自主 Agent 或跨用户云同步。对于图片、音频和视频只保存用户可理解的文本引用与资源标识，不在本版进行多模态理解。

V2.0 不把聊天全文搬进新的数据库，不在每轮强制发起第二次模型请求，不允许记忆编译失败阻断主回复。它不直接改角色卡原始 PNG/JSON，不重写 MVU/SP 数据，不负责把其他模板迁成统一格式；那是 V2.5 的职责。它也不生成图片、灵感牌或二创内容；那是 V3.0 的 Provider 体系。

V2.0 不把自动摘要当权威事实。模型输出只能形成候选，未经规则校验或用户确认的内容必须带 `candidate` 状态，默认不得以强事实注入。世界书仍是设定权威，正式策划成果仍由 V1.1 的版本链管理，聊天楼层仍是事件来源。记忆引擎只做索引、压缩和上下文选择。

## 四、核心用户流程

### 4.1 首次启用

用户在项目设置中打开“轻量记忆”。系统先展示权限和成本说明：保存位置、是否允许读取当前聊天历史、是否允许阶段性调用模型、默认最大注入预算、导出时是否包含记忆。用户确认后，系统创建空的项目记忆仓，不自动扫描所有旧聊天。随后提供三种起步方式：从现在开始、只扫描最近若干楼、从用户选择的章节范围导入。

导入前先生成预览：发现多少候选事件、多少角色或地点别名、预计占用多少空间、哪些内容可能与世界书冲突。用户可取消、调整范围或只导入固定标记的楼层。正式写入后产生一次 `import_batch`，所有记录都保留来源楼号、消息 ID、内容哈希和导入时间，整个批次可一次撤销。

### 4.2 日常回合

主回复请求开始前，上下文构建器接收当前输入、最近对话窗口、当前章节和模块信息。记忆引擎先以本地规则筛选候选：固定记忆、活跃线索、与输入中实体匹配的事件、最近状态变化、当前策划节点引用。然后进行去重、冲突过滤和 token 裁剪，输出只读 `ContextCapsule`。用户可在发送前预览，也可使用“自动发送但保留记录”的快捷模式。

主回复完成后，默认只运行便宜的本地观察器，判断这一轮是否存在明确状态变化，例如出现“得到钥匙”“约定明天见”“任务完成”“人物离场”等结构。观察器不直接固化，而在记忆托盘显示一到数条候选。用户可以逐条确认、修改或忽略，也可以设置“只对高置信、可引用的陈述自动确认”。若启用可选记忆编译器，它只在达到阈值时运行，例如累计若干新楼层、章节收束或用户主动点击，而不是每轮调用。

### 4.3 章节收束

当 V1.1 的小章或大章成果被用户确认时，V2.0 提示生成“章节记忆快照”。快照不是复制整篇大纲，而是包含本章已发生事件、结束状态、遗留线索和关键承诺，并引用正式成果版本 ID。用户审核后可固定为 L0 摘要，同时将已经解决的 L1 线索标记为关闭。若策划成果后来回滚，系统提示关联快照可能过期，但不静默删除历史。

### 4.4 纠错与遗忘

用户发现记忆错误时，可以选择“修正文案”“标记为传闻”“标记已过期”“用新事实取代”或“彻底删除”。修正会建立新修订并保留旧值；取代会建立显式 `supersedes` 关系；彻底删除需要二次确认，并检查它是否被摘要、策划成果或其他记录引用。删除后召回索引立即失效，导出也不再包含正文，只留下可选的匿名墓碑用于防止再次从同一来源重复导入。

### 4.5 搜索与回顾

用户可用自然关键词、实体筛选、章节、状态、标签和时间范围组合搜索。搜索结果按“相关性 + 当前活跃度 + 用户固定 + 来源可信度”排序，每条都显示为什么命中。用户可以把若干记录临时加入下一次请求，也可以创建只读回顾卡。搜索不应依赖模型；在离线环境中仍能完成。

## 五、信息分层：L0 与 L1

V2.0 只维护两层，刻意拒绝继续分裂。L0 是“稳定剧情摘要”，数量少、变化慢，回答这个项目现在进行到哪里、世界发生了哪些不可忽略的变化、当前最重要的目标是什么。L0 按项目和章节保存，每份有严格字符预算，更新必须经过 Diff。它适合在较长间隔后恢复上下文，但不用于记录每个细节。

L1 是“可检索剧情记录”，包括事件、事实、承诺、状态变化、线索和用户固定备注。L1 保留来源、参与实体、发生顺序、置信状态与生命周期。日常召回主要从 L1 选择，再由 L0 提供整体方向。二者都不是聊天正文的替代品；如果需要精确措辞，应跳回原楼层。

不设置 L2 向量库、不设置 L3 知识图谱，也不把每个句子拆成三元组。实体索引只维护规范 ID、显示名和别名，用来匹配“阿梨”“梨小姐”是否指向同一人物。关系仅在确有产品用途时以普通字段表达，例如参与者、地点、拥有者、关联线索；不追求通用图数据库。

L0 的更新来源有三种：用户手工编辑、章节成果确认时生成候选、累计 L1 超出预算时请求压缩。无论来源如何，旧版本都进入历史。L1 的进入来源有四种：用户固定消息、确定性规则候选、可选模型编译候选、从 V1.1 成果引用。每条记录必须标明来源类型，界面上不能把模型推断伪装成人类确认。

## 六、数据模型

项目级 `MemoryStore` 至少包含 `schemaVersion`、`projectId`、`chatScope`、`createdAt`、`updatedAt`、`policy`、`summaries`、`records`、`entities`、`threads`、`batches`、`revisions` 和 `tombstones`。存储采用可迁移的 JSON 结构或宿主提供的设备级持久层，不把大对象塞进单条世界书。若宿主存储有大小限制，按项目分片并维护清单。

`MemoryRecord` 的建议字段如下：稳定 `id`；`kind` 为 event、fact、promise、state、clue、note 之一；`text` 为用户可读正文；`status` 为 candidate、confirmed、superseded、expired、deleted；`confidence` 只表达提取置信而不表达真伪；`importance` 为用户可调等级；`sourceRefs` 指向聊天、楼层、成果版本或世界书条目；`entityIds`、`locationId`、`threadIds` 用于筛选；`storyTime` 与 `sequence` 表达故事内顺序；`visibility` 为 public、restricted 或 manual-only；`createdBy` 标明 human、rule、model、import；`contentHash` 用于幂等去重；`revision` 与时间戳用于冲突检查。

`MemorySummary` 包含 `scope`、`scopeId`、`text`、`includedRecordIds`、`sourceArtifactVersionIds`、`tokenEstimate`、`revision`、`status` 和 `supersedes`。摘要必须能回答“它由哪些记录压缩而来”，不能只保存一段无来源文字。摘要被修订时，旧版本仍可查看和恢复。

`EntityRef` 只保存稳定标识、类型、主显示名、别名和来源绑定。它不保存完整角色档案，角色档案继续来自 V1.1 人物成果或未来统一卡规范。`StoryThread` 保存线索名称、状态、开启与关闭来源、关联记录和可选截止条件，用于让未完事项不因摘要压缩而消失。

`ContextCapsule` 是瞬时对象，不默认持久化全文。它包含请求 ID、选中的 L0/L1 ID、排序分数解释、排除原因、冲突列表、预算统计和最终注入文本哈希。请求日志只保存必要诊断，不复制 API Key、完整聊天或受限记录。用户主动导出诊断时再决定是否包含可读文本。

所有对象都使用稳定 ID，禁止用数组下标作为引用。时间同时保存真实时间和可选故事时间，二者不混用。任何迁移都先验证 schema、生成预览、备份旧分片，再以幂等事务写入；失败时保留旧版本可读。

## 七、召回与排序算法

基础召回完全本地化。第一步从用户输入、最近消息和当前策划节点提取规范化词项，包括中文连续片段、显式人名别名、地点、物品和线索标签；第二步从倒排索引取候选；第三步加入固定记录、活跃线索和当前章节摘要；第四步计算分数并去重；第五步按预算组装胶囊。

建议分数由若干可解释项组成：用户固定权重、实体精确匹配、线索活跃、当前章节关联、近期状态变化、来源可信度、时间衰减和重复惩罚。每项都能在界面显示，不使用不可解释的单一“AI 相似度”。用户可选择偏向连续性、偏向人物、偏向伏笔或最省 token 的预设，但这些预设只调整公开权重。

冲突处理优先于排序。当两个 confirmed 记录对同一状态给出不同值时，若存在显式取代关系则只注入新值并标注旧值；若没有关系，则两条都不作为强事实注入，而在胶囊中加入简短冲突提示。模型不得自行决定哪条是真的。用户解决冲突后，决议作为修订保存。

预算分配先保底：项目 L0、当前章节 L0、最高优先级活跃线索各有上限；剩余预算再给相关 L1。单条过长记录优先使用用户确认的短描述，不能临时让模型改写。达到预算后记录排除原因，用户可手动替换。估算与真实 tokenizer 可能不同，因此还要预留安全余量，若请求适配器反馈超长则按最低损失顺序再次裁剪。

## 八、轻量记忆编译器

编译器是可选能力，不是核心依赖。它接收有限的新增消息、已知实体目录、当前章节和既有相关记录，返回结构化候选 Delta：新增、更新、关闭线索、建议摘要。它不得直接写存储，也不得得到 API Key。调用走 V1.1 的模型配置与模块覆盖，可单独绑定 System 预设和模型，但必须继承统一的安全日志规则。

默认触发条件应保守：用户主动点击；确认章节成果；累计新增内容达到阈值；或者本地观察器发现多个高价值变化。取消生成、空回复、纯 OOC、设置操作和失败请求不触发。一次用户主回复最多允许一次可选编译请求，编译失败不重试风暴，只留下待处理批次。用户可稍后手工重试一次或直接跳过。

结构化结果需经过 schema 校验、来源引用校验、实体存在性校验、长度预算和注入安全检查。模型若引用不存在的楼层、生成来源中没有的事实、输出未知操作或夹带指令，整项进入隔离区而不是部分静默落库。批量候选在界面按新增、变更、冲突、关闭分组，支持逐项确认和全批撤销。

为了控制成本，编译器只处理自上次成功检查点后的增量，并通过内容哈希实现幂等。若跨设备导入导致检查点不连续，应要求用户选择重新扫描范围，不能猜测缺失楼层。编译器所用 prompt、schema 版本和模型描述写入批次元数据，便于将来解释为什么产生某条候选。

## 九、与 V1.1 的集成架构

V2.0 以 `MemoryService` 插件挂到 V1.1 的 Command Core，而不是侵入各 Agent。主控、总纲、大章、小章、人物、推进预设和格式编译都通过同一 `ContextProvider` 请求上下文；提供者返回只读胶囊，各 Agent 不直接查询存储。这样可以统一预算、审计和禁用行为。

建议接口包括：`getCapabilities()` 返回存储与可选编译能力；`prepareContext(request)` 返回胶囊；`observeTurn(turn)` 产生本地候选；`compileBatch(batch, configRef)` 请求可选模型；`confirmDelta(deltaId, selections)` 落库；`search(query)` 本地检索；`revise(recordId, patch, expectedRevision)` 乐观并发更新；`exportProject(policy)` 与 `importProject(payload, mode)` 处理可移植数据；`dispose(chatKey)` 清理监听和内存索引。

V1.1 的请求日志只记录胶囊 ID、记录数量、token 估算和选择原因摘要。若用户打开详细诊断，才在本地临时展示注入正文。项目导出默认可选择“不含记忆”“含确认记忆”“含候选和历史完整包”三档；无论哪档都不包含 API Key、Connection Manager 密钥或模型服务响应头。

世界书集成遵循单向引用优先。记忆可以引用世界书条目及其读取版本，但不自动把聊天记忆写回原世界书。用户明确选择“提升为设定”时，仍走 V1.1 的原世界书 Diff、陈旧拒绝、二次确认、写后重读和撤销流程。世界书更新后若与记忆冲突，V2.0 只提示审查。

正式策划成果同样不被复制。记忆快照保存成果版本 ID 和少量运行事实；成果被回滚或替换时显示关联过期。这样 V1.1 的版本链保持权威，V2.0 不形成第二套大纲编辑器。

## 十、插件接口与扩展点

轻量内核只定义四类扩展：存储适配器、提取器、排序策略和导出过滤器。第三方扩展必须通过能力声明注册，不能拿到全局窗口的任意写权限。每个扩展有稳定 ID、版本、输入输出 schema、权限清单、超时和禁用开关。

`MemoryStorageAdapter` 负责读取分片、按期望修订提交、列出项目、备份与恢复。首发仅提供浏览器设备级适配器和测试内存适配器；云同步不在本版。`MemoryExtractor` 只能接收已脱敏的指定消息范围并返回候选，不得直接写入。`RecallPolicy` 接收候选元数据和请求上下文，返回可解释分数；它不能读取 API Key。`ExportRedactor` 根据用户选择移除受限记录与诊断字段。

所有插件调用都经过超时和错误隔离。某个提取器失败时，记忆中心显示来源和错误，但主回复继续；排序策略失败时回退到内置确定性排序；存储适配器写入失败时保持待提交 Delta 并禁止声称保存成功。插件升级若 schema 不兼容，必须先在副本上迁移并提供回滚。

本版不开放任意脚本市场，不从远程 URL 动态执行未知 Provider，不允许插件修改 DOM 私有节点。未来 V3.0 的创意 Provider 将使用另一套输出契约，不能借记忆接口偷渡生图或二创功能。

## 十一、桌面端界面

桌面端延续 V1.1 三栏工作台。左栏在会话导航下增加“记忆”入口和未审候选计数；中栏可在对话、成果、记忆时间线之间切换；右栏显示当前胶囊、筛选和记录详情。用户不必离开原工作流就能看到本轮注入了什么。

记忆中心顶部提供项目摘要、活跃线索、待确认、全部记录、冲突和回收历史六个视图。列表项必须显示类型、状态、正文首句、来源、相关实体、更新时间和入选原因。批量操作只在明确选择后出现，删除与覆盖采用二次确认。详情页显示完整修订链、来源跳转、引用关系和本轮排除开关。

发送框附近增加小型“记忆胶囊”按钮，显示本轮预计条数和 token。点击后展开，不应自动遮挡消息编辑。用户可以临时移除某条、固定某条或把搜索结果加入本轮；这些临时选择只影响当前请求，除非用户明确保存为规则。

设置页以通俗语言呈现三组参数：保存与隐私、召回预算、可选编译器。高级权重折叠在“召回策略”中，并提供恢复默认。任何需要模型调用的开关旁都显示当前配置来源、可能费用和最近一次执行时间。

## 十二、手机端界面

手机端不能把桌面三栏简单压窄。记忆中心使用单列主区与底部导航，详情和筛选作为可关闭抽屉。顶部保留返回、标题、待确认数和更多菜单；所有按钮至少约 44px，可用触摸操作且不依赖 hover。抽屉打开时锁定背景滚动，点击明确的关闭按钮、返回键或遮罩均可关闭，并必须在 320、375、430px 宽度验证。

本轮胶囊采用输入框上方的折叠条，只显示“摘要 2、记录 5、约 620 token”等关键信息。展开后每条支持向左滑出临时排除，但同时保留可见按钮，避免手势成为唯一入口。批量确认在底部固定操作栏完成，并适配安全区；软键盘弹出时不能盖住保存或关闭。

来源跳转若指向已被宿主裁剪或删除的楼层，应展示“来源当前不可见”而不是无响应。长文本详情使用可选中复制的正文，避免嵌套横向滚动。屏幕旋转、切聊天和工作台关闭时保存草稿选择；重新打开后不会保留已经失效的瞬时胶囊。

真机验收除常规点击外，还要覆盖快速连点、长按选择文本、系统返回手势、软键盘、低性能设备和页面缩放。任何弹窗点不开、关闭后遮罩残留、底栏挡住正文或点击穿透都视为阻断发布的问题。

## 十三、隐私与安全

记忆内容天然比普通设置敏感，因此默认本地、最小收集、明确导出。项目必须按聊天或角色作用域隔离，稳定键不能只用显示名，防止同名角色串数据。切换聊天时清理内存中的搜索结果和瞬时胶囊，所有异步结果提交前再次核对 chatKey 与 projectId。

API Key 仍只由 V1.1 设备级模型配置管理，记忆存储、批次、日志、世界书和项目导出不得出现密钥。Connection Manager 只保存 profile ID。模型编译请求只发送用户选择的消息范围和必要既有记录，不发送全部世界书或其他聊天。独立 API 直连失败时明确报告 CORS、HTTPS 混合内容或不可达，不静默切换代理。

记忆正文在进入提示词前要使用数据边界包装，明确它是叙事资料而非指令。来自聊天、世界书和导入包的文本都视为不可信数据，不能激活命令、加载脚本或改变 System 规则。导入包经过 schema、大小、深度、字符串长度和原型污染检查；HTML 仅以文本显示，不使用不受控 `innerHTML`。

删除分为软删除和彻底清除。软删除进入可恢复历史并停止召回；彻底清除移除正文和索引。用户应能查看各项目占用空间并一键导出后清除。错误报告默认脱敏，只包含类型、版本、对象 ID 和堆栈摘要。

## 十四、失败模式与回退

存储不可用时，系统进入只读或会话临时模式，显著提示“本轮修改尚未持久化”，不能假装成功。索引损坏时从记录分片重建；若分片也损坏，先保留原文件并提供诊断导出，不自动覆盖。空间不足时停止新增并建议清理候选、旧修订或导出，不删除 confirmed 记录。

编译器超时、断流、返回非法 JSON 或模型拒绝时，主回复不受影响，批次标记失败并可手工重试。连续失败触发熔断，本次会话不再自动调用。召回算法异常时回退到“固定记录 + 当前章节摘要”的最小胶囊，并在发送前警告。

来源楼层被删除时记录保留但显示断链；用户可选择保留为手工确认事实或删除。世界书与记忆冲突时停止强事实注入，等待用户决议。跨设备导入发生相同 ID 不同内容时，不采用最后写入覆盖，而生成冲突副本和对比视图。

模块被禁用时，V1.1 继续运行，所有 Hook 和事件监听应释放。卸载不会自动删数据，用户可在卸载前选择导出或清除。升级失败时恢复升级前备份，旧 schema 至少保持只读可导出。

## 十五、性能与容量预算

首发建议将普通项目目标控制在五千条 confirmed/candidate 记录以内，浏览器侧索引初始化在中等手机上目标低于一秒，首次冷启动上限不超过两秒；列表虚拟化后滚动保持流畅。单次召回候选扫描不遍历全部正文，而通过倒排索引和状态桶缩小范围，目标在常见项目中低于五十毫秒。

默认上下文胶囊建议上限为模型窗口的一小部分，并提供绝对 token 上限。项目 L0、章节 L0 和 L1 分别设预算，避免某层独占。记录正文建议短而完整，单条超过阈值提示拆分或保留引用。摘要历史和请求诊断设置保留周期，用户固定的版本除外。

持久化采用增量写和防抖，不能每次输入都重写整个项目。索引可重建，不作为唯一权威；权威记录写入使用预期修订和幂等批次。移动端后台切换前尽快冲刷待提交队列，但不阻塞页面关闭。所有性能预算都要通过合成数据与真实低端设备复核，未测时不得写“已优化”。

可选模型编译的成本预算以次数和输入量双重控制。设置页显示本日调用数、最近输入估算和失败次数。默认不对每轮调用，不对已处理哈希重复调用，不因输出非法自动无限重试。

## 十六、迁移与兼容

从 V1.1 升级时默认创建空记忆仓，不改变既有项目状态。用户选择导入后，系统可读取 V1.1 已确认成果、选定聊天楼层和世界书引用，生成预览批次。策划成果只建立引用，不能复制后反客为主。V1.1 的模型预设和模块绑定可以被记忆编译器引用，但密钥不随项目迁移。

若检测到本地其他记忆插件，仅展示兼容性提示和只读导入入口，不自动接管、不双写。对于结构可识别的数据，可通过适配器映射为候选；无法证明语义的字段保留在原始附件中，要求用户确认。V2.0 不承诺把重型 RAG、知识图谱或角色主观记忆无损降级成公共记忆。

导入采用三阶段：解析与隔离、映射预览、确认提交。每阶段都可取消，提交产生完整批次和回滚点。导出含 schema、应用版本、项目标识、记录、修订、来源引用和可选原始附件，不含密钥。未来 V2.5/V4.0 使用稳定 ID 引用本仓，不能要求用户重新导入同一份历史。

旧版浏览器不支持某些持久 API 时回退到 V1.1 已验证的设备级设置或 localStorage 分片，并显示容量限制。任何兼容回退都不得改变权限或悄悄上传云端。

## 十七、测试与验收矩阵

单元测试覆盖记录规范化、稳定 ID、内容哈希、别名匹配、倒排索引、排序解释、预算裁剪、去重、取代、冲突、生命周期、修订并发、批次幂等、导入导出和脱敏。每个算法必须有中文剧情夹具，包括同名人物、别名、反转事实、时间倒叙、秘密标记、删除楼层和超长文本。

契约测试覆盖 `MemoryService`、存储适配器、ContextProvider 和可选编译器。故意注入超时、异常、非法 schema、重复 Delta、错误来源、跨聊天结果、空间不足和版本不兼容，证明不会污染权威记录或阻断主回复。安全测试覆盖提示注入文本、恶意 HTML、原型污染、超深 JSON、超大导入包和敏感字段扫描。

集成测试至少回放三套长剧情：线性冒险、多人悬疑、跨章节恋爱。分别验证物品归属、未兑现承诺、已关闭线索、人物别名和世界书修订。测试应模拟上下文裁剪，比较启用前后是否召回正确，但不能只用模型主观评分；还要断言胶囊内容、来源和预算。

UI 自动化覆盖桌面主流尺寸和 320/375/430px 手机：首次启用、导入预览、候选确认、搜索、临时排除、冲突解决、修订恢复、导出、彻底删除、抽屉关闭、软键盘和切聊天。所有主要按钮都要实际点击，不能只检查 DOM 存在。

真实宿主验收需要在一次性测试聊天和世界书中完成：运行至少一个章节、关闭再打开工作台、切换聊天、刷新页面、在手机端生成和确认记忆、模拟模型编译失败、导出后重新导入。自动化证据不能替代此门。驾驶员最终确认前，文档和 UI 均保持“V2.0 设计/测试中”，不得标记已发布。

## 十八、依赖前置与版本边界

V2.0 开工前必须满足：V1.1 的模型配置、分支会话、流式交互、成果版本、项目导入导出和世界书事务都已稳定；Command Core 有清晰扩展点；手机关闭与重开无阻断缺陷；请求日志能脱敏；真实宿主能力已取证。若这些前置未满足，先修 V1.1，不以记忆功能掩盖基础问题。

V2.0 交付边界包括公共 L0/L1 记忆、透明召回、本地搜索、候选确认、阶段摘要、可选轻量编译器、导入导出、桌面手机 UI 和完整失败回退。边界外包括角色独立认知、MVU/SP 统一迁移、创意 Provider、云同步、协同编辑和远程 MCP 管理。

版本完成后 V1.1 项目仍可在不开记忆时使用；记忆数据 schema 要为 V2.5 和 V4.0 保留稳定引用，但不预先实现其行为。若需要修复 V2.0，可发布 2.0.x；不要把 V2.5 的迁移器以“顺手兼容”塞入小版本。

## 十九、风险清单与化解策略

最大产品风险是“轻量”逐渐膨胀成另一个 Cortex。化解方式是冻结两层模型、禁止默认向量库、限制模型调用、所有新增字段必须对应用户可见问题。第二风险是摘要幻觉成为事实，化解方式是候选状态、来源校验、Diff、默认不强注入。第三风险是同名角色与跨聊天串记忆，化解方式是稳定作用域、别名确认和异步提交前复核。

第四风险是浏览器存储容量与移动性能。化解方式是分片、增量写、可重建索引、虚拟列表、明确容量面板和低端机预算。第五风险是用户被大量候选打扰，化解方式是高阈值、批次托盘、可选章节触发和“本轮无重要变化”正常化。第六风险是与其他记忆插件双重注入，化解方式是能力检测、醒目标识、默认不接管和可关闭 ContextProvider。

第七风险是隐私泄露到日志或导出。化解方式是字段级敏感扫描、导出分档、受限记录默认排除和本地优先。第八风险是模型服务 CORS 失败导致用户误以为记忆坏了，化解方式是沿用 V1.1 的连接诊断并区分存储、召回、编译三种状态。

## 二十、分期实施建议

阶段 A 只做数据模型、存储、手工记录、搜索、修订和导入导出，建立确定性底座。阶段 B 接入 ContextProvider，实现 L0/L1 预算、排序解释、冲突和本轮胶囊。阶段 C 加入本地观察器、候选托盘和章节快照，但仍不调用额外模型。阶段 D 才接可选编译器和结构化 Delta，并完成成本与失败熔断。

阶段 E 完成桌面与手机交互、低端机性能、安全审计和长剧情回放。阶段 F 进入真实酒馆门，针对真实聊天切换、刷新、移动端键盘和其他插件共存反复修正。每阶段都必须可关闭，关闭后 V1.1 主流程保持可用。

不建议先做漂亮的“记忆脑图”再补权威链，也不建议一开始接 embedding 服务。第一条可玩的纵切应是：用户固定一条事件 → 下一轮在胶囊中看到它及来源 → 生成时被正确注入 → 用户修正并撤销 → 刷新后仍一致。这条链通过后再扩大自动化。

## 二十一、与前后版本的关系

V2.0 建立在 V1.1 的非数据库剧情工作台上，复用模型配置、请求日志、项目作用域、成果引用、世界书安全事务和响应式壳。它不改变 V1.1 的完成定义，也不要求用户先安装数据库。V1.1 的“讨论与策划”成为记忆的输入和上下文消费者，权威仍各归其位。

V2.5 会读取 V2.0 的稳定实体、事件和引用 ID，把 MVU、SP 或其他角色卡数据映射到统一标准，但不会反过来把公共记忆变成数据库表。迁移器产出的角色与字段映射可以改善实体识别，却必须经过用户确认。

V3.0 的灵感、文本加工和生图 Provider 可以消费用户明确选择的记忆胶囊，生成灵感或视觉素材，但默认不得看到全部记忆，也不能把创意结果自动写成事实。Provider 输出若被用户确认为剧情事件，才通过 V2.0 候选入口进入公共记忆。

V4.0 在公共事件账本之上增加每角色独立认知。V2.0 的 confirmed 事件可作为“世界发生了什么”的底层证据，V4.0 再表达“谁看见、谁相信、谁误解、谁忘记”。因此 V2.0 必须从一开始保留来源、可见范围和稳定 ID，但绝不能提前声称拥有角色心智。

## 二十二、发布判定

V2.0 只有同时满足功能、可靠性、隐私、性能、双端体验和真实宿主六类门槛才可发布。任何一类缺失都只能标记预览版。尤其不能因为单元测试全绿就声称长剧情连续性已解决，也不能因为桌面可用就忽略手机端抽屉、软键盘和关闭问题。

发布说明必须列出默认不开启的可选模型编译器、数据保存位置、导出内容、与其他记忆插件共存边界、已验证宿主版本和仍未验证的设备。用户升级只改版本号的合同可以延续，但不可移动旧标签；V2.0 应使用新的不可变版本目录和标签，确保随时可以退回 V1.1/V2.0 之前的稳定版本。

最后的驾驶员问题不是“功能是不是很多”，而是四个更朴素的问题：它有没有记错；错了能不能一眼看见；改了能不能撤回；关掉以后原来的 Riki 还能不能正常工作。四项都用真实证据回答“能”，V2.0 才算完成。
