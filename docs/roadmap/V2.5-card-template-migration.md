# Riki 剧情工作台 V2.5 路线说明：角色卡模板迁移与统一标准

> 文档状态：方向设计稿，不代表迁移器、统一格式或任何兼容适配已经实现。V2.5 的前提是 V1.1 工作台与 V2.0 轻量公共记忆均形成稳定、可导出、可回滚的权威链。本文所称“统一”是 Riki 内部的可审查中间标准，不等于强迫所有角色卡改用同一个运行时。

## 一、为什么需要 V2.5

SillyTavern 角色卡生态的复杂之处不在于文件扩展名，而在于同一张卡可能同时依赖角色字段、世界书、正则、Tavern Helper 脚本、MVU 变量、SP 数据库模板、消息楼层初始化、嵌入式状态栏、远程资源和用户设备设置。两个外观看起来都是 PNG 的文件，运行契约可能完全不同；两个都自称 MVU 的模板，也可能在变量路径、更新规则、校验器和 UI 绑定上互不兼容。

用户希望“有些是 MVU、有些是别的数据库模板，都改成我们的第三版”，真正需要的不是一次粗暴字符串替换，而是一条可解释、可暂停、可回退的迁移管线。V2.5 要把来源卡拆成可审查组件，识别它使用的能力与数据，再映射到 Riki 的统一角色项目标准。能够无损理解的部分自动迁移；语义不确定的部分保留原件并要求用户决策；无法迁移的运行时必须明确标红，而不是生成一个看似成功、实际点不开的成品。

统一标准的价值有三点。第一，V3.0 的创意 Provider 和 V4.0 的角色记忆不必为每种历史模板写一套私有读取逻辑。第二，用户可以在电脑和手机上看懂一张卡由哪些模块组成、哪些数据会被修改、迁移后有哪些差异。第三，Riki 能建立稳定的版本、测试和回滚边界，不再靠“整包脚本能跑”作为唯一证明。

## 二、目标与成功标准

V2.5 的首要目标是建立一个规范化中间表示，暂称 `Riki Card Package`。它应覆盖角色基础资料、提示词片段、世界书条目、状态 schema、初始值、更新规则、UI 绑定、正则、辅助脚本、资源清单、运行依赖、权限和来源证明。中间表示既可以承载完全迁移的内容，也可以承载“保留原样的未知组件”，避免为了统一而丢数据。

第二目标是提供适配器式迁移。首批适配器聚焦用户本地真实存在且可取证的 MVU、SP/数据库模板与普通世界书驱动卡；“自定义”不是万能解析器，而是通过能力探测、字段映射和人工确认逐步完成。每个适配器都有输入版本范围、读取规则、语义假设、输出覆盖率和已知限制。

第三目标是安全可回退。默认只读解析来源，永不原地覆盖 PNG、JSON、世界书或聊天。迁移先产生报告和沙箱包，验证通过后才导出一个新文件；来源文件的哈希、迁移日志、未映射项和回滚说明随包保存。任何失败都能回到来源，不把半成品写进真实聊天。

第四目标是双端可用。电脑端适合批量审查字段和 Diff，手机端也必须能完成单卡导入、风险确认、核心映射、预览和导出，而不是只能看一个“请到电脑操作”的空壳。复杂脚本逐行审查可以标注为桌面推荐，但关键阻断信息和取消入口在手机上必须完整。

成功标准不是“支持导入某个 JSON”。每类已声明支持的模板至少要有一张真实夹具完成发现、解析、映射、验证、沙箱预览、导出和重新导入；迁移前后对关键行为进行契约对照；未知内容无静默丢失；高风险脚本无自动执行；用户可用一份报告准确回答迁走了什么、没迁什么、为什么。

## 三、明确非目标

V2.5 不承诺把所有历史角色卡自动变成百分之百等价的新卡。没有规范、依赖私有 DOM、远程代码、混淆脚本或宿主特定补丁的卡，可能只能部分迁移。产品必须允许结论为 `not-supported` 或 `manual-required`，不能为了覆盖率制造虚假成功。

V2.5 不重新实现 SP 数据库完整运行时，也不把十一张固定表、动态表、剧情推进器、数据库浮窗和安装逻辑塞回 Riki 主体。适配器可以读取这些结构、导出中立 schema 或保留兼容组件，但是否运行旧内核是独立兼容层决策。统一标准描述能力，不等于主工作台承担所有能力。

V2.5 不做 V3.0 的灵感二创、生图、素材库和 Provider 商店；不做 V4.0 的每角色主观记忆；不自动修改来源仓库；不联网下载缺失脚本；不绕过许可证或删除作者署名。它也不承诺从截图、视频或仅有成品界面的卡推断出完整数据模型。

V2.5 不把不可信脚本在迁移过程中执行。解析 JavaScript 时优先静态分析和沙箱文本处理；需要真实宿主行为证据时进入单独的测试门，使用一次性聊天和明确权限。生成的预览不能加载远程代码、调用付费 API 或写用户正式世界书。

## 四、统一标准的设计原则

第一原则是“语义先于字段名”。来源中叫 `好感度`、`favor`、`relationship.score` 的字段不一定完全等价；适配器必须记录映射依据、单位、范围、更新时机和显示方式。若证据不足，宁可生成待映射项，也不按名字猜。

第二原则是“权威分层”。角色基础设定、世界规则、运行状态、策划成果、公共记忆、角色认知、视觉资产各有自己的权威对象。统一包用引用连接它们，不把一切压进一个巨大 JSON 字符串。V2.0 的公共事件可以被状态初始化引用，但不会被复制为数据库表；世界书条目仍通过安全事务修改。

第三原则是“未知可保存”。任何适配器无法解释的字段、脚本、正则标志或资源元数据都进入 `opaqueComponents`，保存来源路径、原始内容哈希、媒体类型、风险等级和迁移建议。导出器可以选择原样携带、隔离附件或明确丢弃，默认不能静默删除。

第四原则是“能力声明而非品牌判断”。系统不只显示“这是一张 MVU 卡”，而显示它实际需要：变量读写、消息楼层初始化、Zod 校验、世界书、正则渲染、嵌入 UI、外部请求、音频或数据库服务。适配器按能力工作，避免把同名框架的不同版本混为一谈。

第五原则是“版本化与可重放”。同一个来源加同一个适配器版本和同一组用户决策，应产生稳定、可比较的输出。迁移步骤、映射决定和修复补丁都保存为 manifest；升级适配器时可以重新运行并查看差异，而不是只能手工重做。

## 五、Riki Card Package 数据模型

包根对象建议包含 `packageVersion`、`packageId`、`sourceProvenance`、`character`、`capabilities`、`components`、`bindings`、`assets`、`migrations`、`validation` 和 `signatures`。包可以用目录形式开发，用 JSON/ZIP 或角色卡载荷形式交付，但权威 manifest 必须是文本可审查的，不能只藏在 PNG 二进制中。

`sourceProvenance` 保存来源文件名、哈希、角色卡规范版本、检测到的运行时、原作者元数据、许可证提示、导入时间和用户备注。它不保存本机绝对隐私路径到公开导出，公开包只保留相对来源标签。若来源是多个文件，逐个列出哈希和角色。

`character` 保存稳定角色 ID、显示名、描述、人格、场景、首条消息、示例对话、创建者注记和扩展字段。它只负责角色卡标准语义，不混入运行变量。无法安全解析的富文本按纯文本保存，并保留原始附件供审查。

`capabilities` 是声明列表，每项包含能力 ID、是否必需、提供者、最低宿主版本、权限、失败回退和验证状态。示例包括 `worldbook.read`、`worldbook.write`、`state.mvu`、`state.table`、`regex.render`、`helper.script`、`ui.embedded`、`network.remoteAsset`、`memory.public`、`memory.role`。未声明能力默认不可用。

`components` 采用注册表而不是固定大对象。常见类型包括 `worldbook-set`、`state-schema`、`state-seed`、`update-rule`、`prompt-fragment`、`regex-rule`、`helper-script`、`embedded-ui`、`message-template`、`test-fixture` 和 `opaque`. 每个组件有稳定 ID、版本、输入输出契约、来源引用、内容哈希、依赖、权限和生命周期。

`bindings` 描述组件之间的精确连接。例如 UI 的 `relationshipValue` 读取哪个规范状态路径，某条更新规则在什么事件后执行，某个世界书条目何时注入，某个提示词如何获得 V2.0 胶囊。绑定必须显式，不允许靠相同字符串或 DOM ID 猜测。

`assets` 保存图片、音频、字体和其他资源的逻辑 ID、相对路径、媒体类型、尺寸、哈希、许可证/来源、预加载策略和缺失回退。远程 URL 仅作为来源或可选镜像，发布包应明确哪些资源必须联网。API Key、cookie 和用户本地绝对路径禁止进入资源清单。

`migrations` 保存每次迁移的适配器、版本、输入范围、用户决定、自动修复、未映射项和输出哈希。`validation` 保存 schema、静态安全、契约、预览和真实宿主证据，状态区分 `not-run`、`pass`、`fail`、`pending`。自动化不得写 `driver-accepted`。

## 六、来源发现与分类

导入开始后先进行纯读取发现。系统识别 JSON 卡、PNG 载荷、世界书 JSON、Tavern Helper 脚本、正则集合、MVU 初始化消息、数据库 DDL/模板和伴随资源。发现器只根据可验证标记给出置信结果，并列出证据，如字段路径、脚本签名、世界书条目名称或声明版本。

分类结果不是单选标签，而是一张能力图。一张卡可能同时被识别为 `card-v2 + worldbook + mvu + regex + helper-script + remote-assets`。系统标出必需与可选依赖、已找到与缺失依赖、可能冲突的重复运行时。用户可纠正分类，并将决定保存为本次迁移规则。

如果 PNG 载荷损坏、JSON 深度异常、压缩包含路径穿越、脚本尺寸超限或字段包含可疑密钥形状，导入进入隔离态。隔离态允许查看报告和导出原件哈希，不渲染嵌入 HTML、不执行脚本、不解压到工作区之外。

发现阶段还要建立“来源组件清单”：每一世界书条目、变量 schema、初始值块、正则、脚本、UI、远程依赖和资源都有一行状态。这个清单是后续覆盖率的分母，防止迁移器只处理成功部分后宣称 100%。

## 七、迁移流水线

迁移采用九个明确阶段：接收、隔离、发现、解析、规范化、映射、验证、预览、导出。每个阶段都有输入输出 schema、可取消点和错误状态。用户关闭工作台后可恢复任务，但恢复前重新校验来源哈希，避免文件被替换。

接收阶段复制或读取来源到只读沙箱并计算哈希；隔离阶段做大小、路径、内容类型和敏感信息扫描；发现阶段生成能力图；解析阶段把已知格式转换成来源 AST 或结构对象；规范化阶段统一编码、稳定 ID、布尔值、数字范围和引用；映射阶段运行适配器并收集用户决策。

验证阶段不只校验 JSON schema，还做引用完整性、状态路径、更新规则、正则目标、资源存在性、权限和宿主能力检查。预览阶段在不写真实聊天的环境中展示角色信息、世界书注入、状态栏和典型状态变化。导出阶段生成新包、迁移报告、校验摘要和可选角色卡文件；任何失败都不改来源。

流水线记录 `MigrationJob`：任务 ID、来源清单、阶段、进度、决定、警告、错误、输出和审计时间。重试从最近安全检查点开始，适配器更新后强制重新验证。用户可以克隆任务比较两套映射，不会覆盖先前结果。

## 八、MVU 适配器

MVU 适配首先确认实际版本与依赖，而不是只搜索 `mvu` 字样。它需要识别变量存放位置、初始化楼层、schema/Zod 约束、更新命令或提示词、消息层级、渲染 UI 的读取路径、事件钩子和失败行为。缺少任一关键证据时，相关能力状态保持待确认。

规范化输出将变量结构转换成 `state-schema` 和 `state-seed`，保留字段类型、默认值、枚举、范围、可空性和说明。更新规则转换成显式触发器与 Patch 契约；不能确定的自由文本规则保留为 `prompt-fragment`，并标注仍依赖模型遵守。UI 中的变量绑定转成稳定路径，不再通过字符串拼接猜字段。

若来源使用消息楼层作为变量权威，迁移器不会直接搬运历史楼层。它生成初始化计划和数据快照，用户选择新聊天安装时再由宿主适配器执行。安装前显示将创建或修改哪些楼层、能否撤销、切换聊天如何隔离。V2.5 本身先提供沙箱计划，真实安装是单独权限门。

对于 schema 演化，MVU 适配器生成从来源版本到规范版本的确定性迁移函数和夹具。字段重命名、类型转换、默认填充与弃用逐项列出；无法转换的值进入隔离区。不得通过 `eval` 执行来源迁移脚本。

## 九、SP 与其他数据库模板适配器

数据库适配的核心是读取“数据语义”，不是把旧运行内核嵌回主包。适配器识别表、列、主键、默认值、枚举、约束、注释、初始化数据、更新来源和 UI 消费者，生成中立 `state-schema`、`state-seed` 与实体集合。固定表名不能直接成为统一标准的永久 API。

每张来源表生成覆盖率报告：哪些列能映射到角色、关系、场景、任务、物品、时间线或自定义域；哪些列只对旧运行时有意义；哪些触发器或计算列无法静态理解。主键与引用必须稳定化，禁止用显示名连接不同实体。动态表定义作为可选模板组件保留，不在迁移时实例化无限表。

旧数据库推进、章节判定和运行期钩子不能因为能解析就自动启用。若用户需要兼容运行，输出一个隔离 `legacy-runtime-adapter` 能力声明，列出其权限、宿主依赖和风险，并要求真实宿主测试。Riki 核心只消费规范查询接口，不能直接调用旧全局函数。

其他自定义数据库模板通过声明式映射表接入。映射表指定来源路径、规范目标、转换器、验证器和冲突策略，支持预览和逐项覆盖。任意 JavaScript 转换器不进入首发；必要的数值、日期、枚举和字符串转换由内置安全函数完成。

## 十、普通世界书与脚本卡适配

不少角色卡没有结构化数据库，但通过世界书条目、正则和 Tavern Helper 脚本形成事实上的运行系统。适配器先保留世界书原有顺序、启用状态、关键词、深度、位置、概率、递归与其他宿主标志，任何无法确认的字段原样记录。条目正文视为不可信数据，不执行其中的 HTML 或命令。

脚本适配器做静态能力盘点：读写哪些变量、监听哪些事件、访问哪些 DOM、发起哪些网络请求、加载哪些远程模块、是否操作世界书或聊天楼层。它可以把明显的配置常量和绑定提取到 manifest，但不能承诺自动重写任意脚本。高风险行为如动态执行、宽泛 `postMessage`、远程代码和密钥形状必须阻断默认导出。

正则适配器保留方言、来源位置、目标范围、深度、启用状态和布尔标志，并用固定夹具验证替换前后。仅凭 JavaScript RegExp 测试通过不足以证明酒馆正则行为等价；需在真实宿主验证显示与提示词两个目标。

若卡只有普通文本与世界书，迁移可以很轻：规范化角色字段、建立条目组件、列出能力并导出。统一标准不要求给简单卡强行加状态 schema、UI 或记忆模块。

## 十一、字段映射与人工决策

映射界面按“已确定、需确认、无法迁移、保留原样”分组。每一项显示来源路径、示例值、目标字段、转换规则、证据和影响消费者。用户改动目标时，系统实时检查重复映射、类型冲突和断开的 UI/规则引用。

常见决策包括实体合并、别名、数值范围、时间格式、枚举归一、空值含义、状态权威、秘密可见性和旧脚本保留。系统提供推荐但不伪装成确定。推荐必须说明依据，例如“来源 schema 明确限制 0–100”，而不是“AI 认为像好感度”。

映射决定保存为可复用 `MappingRecipe`，包含适用来源签名和版本范围。下次导入相同模板可自动套用并仍显示 Diff；来源结构变化时 recipe 失效或部分应用，不能盲目沿用。用户可以导出 recipe 分享，但它不包含角色内容或私密数据。

批量迁移时先在样本卡上确认 recipe，再对其他卡生成逐卡报告。任何一张出现新字段、不同脚本哈希或验证失败，必须单独停下，不因同目录而假设结构相同。

## 十二、统一插件接口

V2.5 定义 `CardAdapter` 契约：`probe(input)` 返回能力证据与置信；`parse(input, limits)` 返回只读来源模型；`plan(source, decisions)` 返回迁移计划；`transform(plan)` 产生规范组件；`validate(package)` 返回结构化问题；`renderPreview(package, hostCaps)` 只生成安全预览描述；`export(package, format)` 生成交付物。所有方法可取消、超时且不得越权写宿主。

`ComponentValidator` 按组件类型注册，输出稳定问题码、严重级别、路径、证据和修复建议。`PackageExporter` 只负责已批准格式，PNG 嵌入器与 JSON 导出器分离。`HostInstaller` 是独立能力，默认不包含在迁移任务中；真正写聊天、世界书或扩展设置前必须再次确认。

适配器清单包含 ID、版本、作者、支持输入、输出 package 范围、权限、许可证和签名。首发不提供在线商店或远程动态加载；适配器随版本打包或由用户本地明确安装。未知适配器不能获得脚本执行权限。

未来 CLI/MCP Companion 可以调用同一迁移 Command Core 完成批量扫描、报告和构建，但远程 Agent 只能在用户授予的目录与任务作用域操作。CLI 成功不等于真实宿主安装成功，二者证据分开。

## 十三、与 V2.0 记忆的连接

统一包可以声明角色、地点、物品和线索的稳定实体 ID，为 V2.0 的别名匹配提供更可靠目录。但迁移器不得重写现有 confirmed 记忆。若发现实体可能相同，生成合并提案，用户确认后建立别名或 `sameAs` 映射，并保留撤销。

来源卡中的“历史摘要”“角色记忆”“事件表”不自动当作世界事实。它们按来源语义导入为候选附件：客观事件可映射到 V2.0 candidate，角色主观描述保留到 V4.0 兼容区，纯设定进入世界书候选，运行缓存可选择丢弃。每类都显示数量和示例。

迁移后的角色项目可引用 V2.0 的公共记忆能力，但默认关闭，用户在新聊天中启用。包只声明兼容版本和需要的作用域，不内嵌用户现有记忆。公开分享角色卡时不会泄露私人剧情历史。

## 十四、桌面端 UI

桌面端采用“任务列表—组件清单—详情/Diff”三栏。左栏显示迁移任务和阶段；中栏显示来源组件及映射状态；右栏显示字段、风险、依赖、预览和用户决定。顶部始终可见来源哈希、当前阶段、未处理阻断数和取消按钮。

发现报告用能力矩阵呈现，但避免只有颜色；每个格子同时有文字状态。字段映射支持搜索、按严重级别筛选、展开来源样例和目标消费者。脚本与正则查看器只读显示并提供精确行号、风险标记和复制，不直接执行。

Diff 分为语义 Diff 和文本 Diff。语义 Diff 告诉用户增加/删除了哪些组件、字段、依赖和权限；文本 Diff 用于世界书、提示词和脚本。二进制资源显示哈希、尺寸和缩略图，不伪造逐字节视觉等价。

导出前提供最终清单：输出格式、文件、大小、能力、未迁移项、需真实宿主验证项、许可证提示和回滚方式。按钮文案区分“生成沙箱包”“导出新角色卡”“安装到测试聊天”，不能用一个“完成”混淆不同权限门。

## 十五、手机端 UI

手机端以阶段向导为主，每屏只解决一个决策：选择来源、查看风险、确认能力、处理核心映射、预览、导出。顶部进度显示可返回的阶段，底部固定“保存草稿/继续”。所有触控目标至少约 44px，安全区和软键盘适配必须实测。

组件清单使用单列卡片，卡片显示状态、名称、类型和阻断原因；点击进入全屏详情。字段映射不使用宽表，而用“来源 → 目标”纵向卡，支持搜索选择目标和查看示例。长脚本只提供风险摘要与只读文本，明确建议在桌面深审，但用户仍可在手机选择隔离或放弃。

预览中的嵌入 UI 必须运行在严格沙箱或静态快照中，不能让来源脚本接管手机页面。关闭按钮、系统返回、遮罩和手势路径均需验证；迁移任务在浏览器进入后台后可恢复，不出现重复导出。

手机端导入文件选择受系统限制时，提供清晰说明和替代路径，例如从酒馆当前角色读取或选择已保存的项目包，但不能偷偷扩大读取目录。导出后显示文件名、哈希和保存建议，不能只弹“成功”。

## 十六、隐私、安全与供应链

所有来源均视为不可信。解析器设置文件数、单文件大小、JSON 深度、解压总量和处理时间限制，防止压缩炸弹和资源耗尽。路径必须规范化并限制在任务沙箱。HTML、SVG 和 Markdown 中的活动内容默认禁用；预览只渲染经过清洗的安全子集。

脚本安全审计关注动态执行、远程模块、任意网络、宽泛消息通道、私有 DOM、凭据形状、设备存储遍历和隐式宿主写入。风险报告给出证据路径与严重级别。高危组件默认隔离，用户即使选择保留，也要在输出 manifest 中标记并在真实安装前再次确认。

迁移日志和公开报告不得包含 API Key、cookie、Authorization、完整本地路径或私人聊天正文。敏感扫描命中时先遮罩，再让用户决定是否继续。来源许可证、作者、版本和修改说明尽量保留；工具不声称自动解决版权与再发布许可。

适配器本身也是供应链边界。发布内置适配器需固定源码、依赖、哈希和审查记录；不从 `latest` 动态更新。包的签名只证明构建来源，不证明内容安全。导入第三方统一包仍需重新验证。

## 十七、失败回退与恢复

任何阶段失败都保留只读来源和最后安全检查点。解析失败时导出诊断，不尝试用正则硬扒整个文件；映射失败时允许保存人工决策；验证失败时仍可导出“报告包”，但禁止标成可安装成品。关闭或崩溃后恢复任务时复核来源哈希和适配器版本。

输出写入采用新文件和临时目标，完成校验后再呈现给用户，不覆盖来源。若导出中断，删除或隔离不完整临时文件并显示恢复建议。真实宿主安装若部分成功，安装适配器必须有操作日志和逆向撤销步骤；无法保证原子时提前说明可能残留。

未知字段默认保留在 opaque 组件，空间不足或格式不支持时要求用户明确“隔离附件”或“放弃”，不能自动丢弃。资源缺失时预览使用占位符并列出缺失清单；远程资源不可达不触发自动下载其他来源。

适配器升级造成输出差异时提供新旧包语义 Diff，用户可以继续使用旧适配器版本。旧包至少可读、可导出；若必须迁移 package schema，先备份并支持回退。

## 十八、性能与容量预算

普通单卡发现和解析在桌面目标数秒内完成，手机上要分阶段让出主线程并显示真实进度。大卡或包含大量资源时按组件流式处理，不能一次把所有二进制复制到内存。解析器设硬上限并允许用户在确认后提高，但提高不代表放宽安全路径。

组件清单和 Diff 使用虚拟列表；文本比较对超大脚本采用分块与摘要，用户可按需加载完整内容。哈希计算增量进行并可取消。预览只加载当前可见资源，图片生成缩略图有尺寸与数量预算。

批量迁移默认串行或低并发，避免手机耗电和浏览器崩溃。每个任务独立检查点，单卡失败不污染其他卡。缓存只保存可重建解析结果并与来源哈希绑定；用户清理任务时能同步清理缓存。

统一包本身设 manifest 和组件大小预算，超过时报告主要占用者。远程资源与内嵌资源的取舍由用户决定并记录，不为了小文件默认依赖不稳定 URL。

## 十九、验证与测试

每个适配器需要三类夹具：最小合法、真实复杂、恶意或损坏。测试断言发现证据、组件分母、字段映射、未知保留、稳定输出、幂等重跑、迁移报告和导入回读。真实夹具必须有来源许可或仅在本地私有测试中使用，公开仓库不误传用户卡。

schema 测试覆盖 package 根对象、组件、绑定、能力、资源和迁移记录。引用完整性测试确保 UI、规则和世界书引用存在；状态测试覆盖类型、默认值、边界和升级；正则测试覆盖来源与目标方言；脚本静态测试覆盖风险模式和误报审查。

端到端测试至少包含：普通世界书卡迁移；一张 MVU 卡状态初始化与 UI 绑定；一张数据库模板的表/列/引用映射；一张混合脚本卡的部分迁移与 opaque 保留；一个损坏包的隔离；一个适配器版本升级的 Diff。每条链都从来源哈希开始，到输出重新导入结束。

UI 自动化逐个点击导入、阶段导航、筛选、映射、冲突处理、预览、导出、取消和恢复，覆盖桌面与 320/375/430px。必须检查没有横向溢出、抽屉可关、底部按钮不被键盘遮挡、长文件名和中文字段不破版。

真实 SillyTavern 门只对声明可安装的输出执行。使用一次性角色和测试聊天，验证世界书条目、初始化状态、变量更新、正则渲染、嵌入 UI、切聊天、刷新和卸载。自动预览不能替代。对于部分迁移输出，验收结论必须逐能力列出，不使用笼统“迁移成功”。

## 二十、依赖前置与版本边界

V2.5 开工前，V2.0 的稳定项目/实体 ID、导入导出、隐私过滤和修订机制必须定型；V1.1 的世界书事务、模型配置与 Command Core 必须可复用。角色卡相关 API、MVU、Tavern Helper、正则与宿主能力要以固定版本声明或真实源码取证，不能靠记忆写接口。

首版范围建议冻结为三类适配：标准角色卡 + 世界书、一个明确版本族的 MVU、一个明确版本族的 SP/数据库模板。每类先完成端到端纵切，再扩充版本。自定义适配器框架可以交付，但不得宣传“支持所有模板”。

V2.5 的完成边界包括统一包规范、能力清单、迁移任务、适配器契约、三类首发适配、字段决策、沙箱预览、报告、导出和双端 UI。边界外包括在线适配器市场、任意脚本自动改写、批量发布平台、V3 创意生成和 V4 角色认知。

修复发布用 2.5.x。若需要引入新的 package 主版本或改变权限模型，应进入独立大版本讨论，不在补丁版本静默破坏旧包。

## 二十一、风险与治理

最大风险是把“格式转换成功”误当“运行行为等价”。治理方式是能力级验收、真实宿主门、覆盖率分母和未迁移清单。第二风险是未知字段丢失，治理方式是 opaque 组件与明确放弃决定。第三风险是适配器误判版本，治理方式是证据化 probe、版本范围和置信状态。

第四风险是执行恶意脚本，治理方式是全程静态解析、沙箱预览、权限声明和高危隔离。第五风险是重做所有旧运行时导致范围失控，治理方式是中立 schema 与 legacy adapter 边界。第六风险是统一标准过度抽象，导致简单卡也难以理解；治理方式是组件按需存在、提供最小包和人类可读 manifest。

第七风险是手机端无法处理复杂迁移，治理方式是单卡向导、纵向映射、任务恢复和桌面推荐而非强制。第八风险是版权和来源信息在导出时丢失，治理方式是 provenance、许可证提示和修改记录。第九风险是公开包泄露私人剧情或密钥，治理方式是分层导出与敏感扫描。

## 二十二、分期实施

阶段 A 定义最小 package schema、来源清单、能力声明和只读解析框架，用普通角色卡完成往返。阶段 B 建立 MVU 适配器纵切：发现 schema、初始化、更新规则和 UI 绑定，输出沙箱包。阶段 C 建立数据库模板纵切：表、主键、引用、初始数据和未知运行时隔离。

阶段 D 完成映射 UI、recipe、语义 Diff、迁移报告和任务恢复。阶段 E 加入脚本/正则静态风险、资源清单、PNG/JSON 导出器。阶段 F 做桌面与手机 QA、安全审计、性能和批量任务。阶段 G 才进入真实宿主安装验证，并按能力修正。

每阶段均有可交付的只读报告，不能因为安装器未完成就让前期成果不可用。第一可玩纵切应是一张简单卡：导入 → 看到完整组件清单 → 迁成最小统一包 → 导出新文件 → 重新导入逐项一致。第二纵切再加入 MVU 状态变化，第三纵切加入数据库映射。

## 二十三、与前后版本的关系

V2.5 不替代 V1.1 的剧情助手，而把角色项目变成它能稳定理解的输入。迁移后的世界书仍由 V1.1 的库存、条目选择、Diff 和写回机制管理；模型配置仍是设备级，绝不打包密钥。

V2.0 提供公共事件与稳定实体引用。V2.5 可以改善实体目录、把来源历史映射为候选，却不改变记忆真相。未来 V4.0 会使用统一包中的角色 ID、可见性、角色状态和关系定义建立独立记忆生态，因此这些字段现在要稳定、可版本化，但不提前执行认知推理。

V3.0 需要一个清晰的项目与资源边界来挂载多个灵感/生图 Provider。V2.5 的 capabilities、assets、permissions 和 bindings 正好提供这个挂点。Provider 能声明它读取哪些组件、输出哪些资产，但不能直接修改来源卡或绕过迁移报告。

## 二十四、发布与用户承诺

发布时必须明确列出支持的来源版本、部分支持项、完全不支持项、已验证宿主版本和测试卡类型。营销文案不能写“一键兼容所有 MVU/数据库卡”，除非有逐版本证据。每个导出都附迁移摘要和未解决风险，让用户即使半年后也能理解这个包从哪里来。

版本分发继续遵循不可变目录与标签。用户可以只改加载器版本号进入 V2.5，但来源卡迁移属于显式任务，不会在升级时自动发生。旧 V2.0 项目保持可读，统一包升级先预览后提交。

最终完成判定要回答：来源有没有被改；每一个来源组件是否有去向；未知和高风险是否被诚实标出；输出是否能重新导入；关键运行能力是否在真实宿主逐项验证；手机和电脑是否都能完成核心流程。只有这些证据齐全，V2.5 才能从路线说明变成已交付版本。
